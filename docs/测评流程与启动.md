# OC-Harness-eval 测评流程与启动指南

在 **OptraCall 产品环境**里测评 Agent 能力。当前三类：**skill**、**sap-method（SAP 分析方法）**、**memory（跨事项经验）**，均完整可用。

> **红线**：测评只读使用 OptraCall 产品——复制 checkout、独立 Host 实例、既有公开 flag。**绝不**改产品源码、写真实数据根（`~/.optracall`、`~/OptraCallProjects`）、连接/停止/修改运行中的服务。详见 [AGENTS.md](../AGENTS.md)。

> **怎么写任务 prompt 与 Fixture**：见 [案例与 Prompt 编写指南](案例与prompt编写指南.md)，示例套件在 `suites/examples/`（skill / sap-method / memory 各一）。

---

## 一、测评是怎么跑的（通用流程）

两类测评共用同一条受控对照流水线：

```
准备隔离环境 → 预检模型 → 冻结计划 → 跑两侧（唯一变量不同）→ 取证 → 分层判分 → 门禁结论 → 留痕
```

1. **准备隔离环境**：复制 OptraCall checkout 到 `runs/<run-id>/optracall-env/{baseline,skill}/code`；每侧独立 dataRoot/projectsRoot；每次 attempt 全新项目。
2. **预检模型**（离线、不触网）：核验本地 Pi 目录中的精确模型身份与原生额度。
3. **冻结计划**：候选身份、题集、模型、重复次数、评委轮数、断言、阈值写入 `run-manifest.json`，看结果前冻结。
4. **跑两侧**：都经 OptraCall 正常任务入口（Host HTTP → 统一会话层 → Pi SDK）。唯一变量：
   - skill 测评：目标 skill 包有无（baseline codeRoot 删包）。
   - memory 测评：记忆能力开关（`--disable-experience-learning` Host flag）。
5. **取证**：native 会话 JSONL（工具调用轨迹）、`060_reports` 交付物、`020_clean` 过程文件、三目录哈希、usage。聊天自述只作过程记录。
6. **分层判分**：规则断言（客观、可复算）优先 → 匿名盲评（win/tie/loss）→ 规则纠偏 → 任务等权增益 + 保守 95% Hoeffding 区间。
7. **门禁结论**：覆盖率 ≥ 70%、超时率 ≤ 20%、全样本胜率下界 ≥ 50%、增益 ≥ 10pp、最低 4 对计分样本；不达标判 `inconclusive`。
8. **留痕**：全部产物落 `runs/<run-id>/`，每个数字可追溯。

**失败即数据**：崩溃/超时/空输出/判失败全计入分母，不选择性重跑；Host 级故障停批保全证据。

## 二、启动前的准备（两类共用）

### 0. 测评前先对齐评测工具（按需）

评测不必与产品持续同步。**发起测评前**调用 `/skill:eval-align`（或说「更新下评测工具」）：它跑契约探针检查评测工具与当前 OptraCall 产品是否适配，不适配就修评测工具适配器（绝不改产品），修好告知「可以测了」。也可直接跑：

```bash
node --experimental-strip-types scripts/eval-align.ts --checkout <checkout> --node <node25+>
```

全 ✅ 即可发起测评；有 ❌ 按 skill 指引修对应接缝。详见 [eval-align skill](../skills/eval-align/SKILL.md)。

### 1. 凭证隔离 HOME

```bash
bash scripts/setup-pi-home.sh        # 默认建在 ~/.skill-eval/pi-home
```

`~/.skill-eval/pi-home/.pi/agent/auth.json` 须含：
- `minimax-cn` 的 `api_key`（被评模型）
- `xiaomi-token-plan-cn` 的 `api_key`（评委模型）

不触碰真实 `~/.pi` 或 `~/.optracall`。

### 2. Node 解释器

OptraCall Host/worker 需 **Node 25+**。当前解释器不足时用 `--optracall-node /path/to/node25+` 指定。

### 3. OptraCall checkout

提供产品源码 checkout（须已 `npm ci`）。环境准备只读复制它，排除 `node_modules/.git/dist/.runtime/.local`。

### 4. 预检（不产生费用）

```bash
npm run eval -- preflight \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home
```

## 三、skill 测评（完整可用）

测一个 SKILL.md 是否真被激活、激活后是否真改善输出。

### 启动

```bash
npm run eval -- eval \
  --suite suites/optracall-smoke.json \
  --optracall /path/to/OptraCall \
  --optracall-node /path/to/node25+ \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home \
  --repeat 1 --judge-repeat 1
```

- 套件须声明 `optracall` 段（`skillName`、`templateDir`）；目标 skill 取自 checkout 的 `extensions/analysis-assets/<skillName>`。
- 现有套件：`optracall-smoke.json`（单题冒烟）、`optracall-data-analysis-v1.json`（data-analysis 草案）。
- 规模 = `任务数 × repeat × 2` 被评会话 + `任务数 × repeat × judgeRepeat` 评委会话。**真实运行产生费用，开跑前确认规模。**

### 判读

看 `runs/<run-id>/REPORT.md` 与 `summary.json`：
- **激活率**：baseline 0、skill 侧读取 skill 包 = 强激活。
- **断言通过率 / 胜率 / 规则纠偏胜率 / 增益区间**。
- **结论**：`effective` / `inconclusive` / `ineffective`。单题冒烟通常是 `inconclusive`（证链路通，不证有效）。

### Qoder 编排

调用 `/skill:skill-eval-flow`，按状态机 S0→S4 引导（收集输入→环境自检→套件冻结→对照评估→解读报告）。

## 四、A 族能力测评（memory / SAP 方法）

统一的可配置「装/不装」对照：唯一变量是某个知识/记忆能力的有无，由 Host flag 承载，复用同一套能力开关模式与计分引擎。

| 能力 | Host flag | 取证工具 | 成功使用判据 | 状态 |
| --- | --- | --- | --- | --- |
| memory（M6 跨事项经验） | `--disable-experience-learning` | `read_case_sources` | find 或 read 成功 | ✅ 完整可用 |
| sap-method（SAP 分析方法） | `--disable-sap-methods` | `read_semantic_context` | 须读到 sap-method 目标 | ✅ 完整可用 |

### 设计

- **唯一变量**：baseline 侧 Host 带 disable flag（能力关），treatment 侧不带 + 注入合成 Fixture。两侧 codeRoot 逐字节一致。
- **取证**：从 native 会话提取对应工具的成功调用（`consulted`＝成功使用）。memory 工具整体禁用，find 成功即算；SAP 是共享工具仅禁 sap-method 内容，故须真正读到 sap-method 目标才算（find 空结果不算）。
- **Fixture 注入**：memory 注入 Case 判断卡片（直写评测 Case SQLite，含 v1→v2 迁移）；sap-method 经 API 建方法并发布。全部只写评测 dataRoot，不碰真实产品。
- **复用**：能力开关模式 + runner 按 id 判 baseline + 计分引擎；能力使用映射为激活率。

### 启动

```bash
npm run eval -- capability-eval \
  --suite suites/optracall-memory-smoke.json \
  --optracall /path/to/OptraCall --optracall-node /path/to/node25+ \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home --repeat 1 --judge-repeat 1
```

- `memory-eval` 是 `capability-eval` 的别名（兼容旧入口）。
- 套件声明 `optracall.capability`（memory/sap-method）+ `capabilityFixtures`。
  - memory：`{caseTitle, judgment:{kind,title,statement}}`。
  - sap-method：`{title, content:{conditions,logic,judgment,limits}}`。
- 现成套件：`optracall-memory-smoke.json`、`optracall-sap-smoke.json`。
- 看 `runs/<run-id>/REPORT.md`：激活率＝能力成功使用率；`cases/treatment/<task>/<attempt>/optracall/memory.json` 是行为取证。
- 单题冒烟通常 `inconclusive`（证链路通，不证有效）；正式测评需扩独立任务与重复。

### 离线端到端验证（无费用）

```bash
node --experimental-strip-types scripts/optracall-capability-integration.ts \
  --checkout <checkout> --node <node25+> --capability memory   # 或 sap-method
```

memory、sap-method 两者均已验证：处理侧注入→查读→取证正例成立，基线能力关闭。

## 七、报告模板与指标说明

每份 `REPORT.md` 的结构固定如下（skill 与 memory 通用）：

```
# 评估报告：<套件名>
> 运行标识 · 生成时间

## 结论摘要        判定 + 核心指标对比表 + 「指标怎么读」大白话解释
## 1. 候选身份      skill/Fixture 路径、内容哈希、版本、套件哈希
## 2. 运行配置      模型、评委、SDK、重复、轮数、token、成本、证据目录
## 3. 证据层级      真实运行 / 事件取证 / 断言 / 评分载体 / 计分范围
## 4. 激活情况      各侧激活率（skill＝读取率；memory＝成功查读率）/ 弱激活 / 误触发
## 5. 判定结果      5.1 汇总  5.2 用例明细  5.3 断言明细  5.4 白送断言筛查
## 6. 规则与评委的分歧
## 7. 未验证项与限制
## 8. 优化建议      待核查项 / 失败模式归类 / 逐条明细 + 下一步
## 9. 结论          判定 + 结论边界
```

**结论摘要下自动附「指标怎么读（大白话）」表**，方便非专业读者一眼看懂：

| 指标 | 它是什么 | 怎么看 |
| --- | --- | --- |
| 激活率 | 装 skill（或开记忆）后模型真去读 skill / 查记忆的比例 | 越高越常被触发；低＝没被用上 |
| 原始评委胜率 | 匿名评委觉得「装 skill 答案更好」的比例 | 仅参考，样本少时波动大 |
| 覆盖率 / 胜率下界 | 该判的配对判了多少；把没判和失败都算输后的保守胜率 | 覆盖 ≥70%、下界 ≥50% 才稳 |
| 规则纠偏胜率 | 用客观断言校正评委后的胜率 | **正式判定看这个** |
| 断言条目通过率 | 预设硬性检查通过的比例 | 两侧对比看改善，仅描述 |
| 任务等权配对增益 | 装 skill 比不装平均多通过多少 pp，带 95% 置信区间 | **区间跨 0＝证据不足**；≥+10pp 且不跨 0 才显著 |
| 平均耗时 / token | 是否更慢更费 | expensive＝成本偏高 |
| 判定 | effective / inconclusive / ineffective | 单题冒烟通常 inconclusive，属正常 |

> 核心一句话：**激活率高 ≠ 有用**。看「规则纠偏胜率」和「增益区间」——区间不跨 0、增益达标才算真正有效；样本不够就判「证据不足」，这是诚实不是失败。

真实样例见 `runs/run-20261115-144512-216e0c06/REPORT.md`。
