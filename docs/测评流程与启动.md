# OC-Harness-eval 测评流程与启动指南

在 **OptraCall 产品环境**里测评 Agent 能力。当前保留两类：**skill** 与 **memory**，均完整可用。

> **红线**：测评只读使用 OptraCall 产品——复制 checkout、独立 Host 实例、既有公开 flag。**绝不**改产品源码、写真实数据根（`~/.optracall`、`~/OptraCallProjects`）、连接/停止/修改运行中的服务。详见 [AGENTS.md](../AGENTS.md)。

---

## 一、测评是怎么跑的（通用流程）

两类测评共用同一条受控对照流水线：

```
准备隔离环境 → 预检模型 → 冻结计划 → 跑两侧（唯一变量不同）→ 取证 → 分层判分 → 门禁结论 → 留痕
```

1. **准备隔离环境**：复制 OptraCall checkout 到 `runs/<run-id>/optracall-env/{baseline,skill}/code`；每侧独立 dataRoot/projectsRoot；每次 attempt 全新项目。
2. **预检模型**（离线、不触网）：核验本地 Pi 目录中的精确模型身份与原生额度。
3. **冻结计划**：候选身份、题集、模型、重复次数、评委轮数、断言、阈值写入 `run-manifest.json`，看结果前冻结。
4. **跑两侧**：都经 OptraCall 正常任务入口（Host HTTP → 统一会话层 → Pi SDK）。唯一变量：
   - skill 测评：目标 skill 包有无（baseline codeRoot 删包）。
   - memory 测评：记忆能力开关（`--disable-experience-learning` Host flag）。
5. **取证**：native 会话 JSONL（工具调用轨迹）、`060_reports` 交付物、`020_clean` 过程文件、三目录哈希、usage。聊天自述只作过程记录。
6. **分层判分**：规则断言（客观、可复算）优先 → 匿名盲评（win/tie/loss）→ 规则纠偏 → 任务等权增益 + 保守 95% Hoeffding 区间。
7. **门禁结论**：覆盖率 ≥ 70%、超时率 ≤ 20%、全样本胜率下界 ≥ 50%、增益 ≥ 10pp、最低 4 对计分样本；不达标判 `inconclusive`。
8. **留痕**：全部产物落 `runs/<run-id>/`，每个数字可追溯。

**失败即数据**：崩溃/超时/空输出/判失败全计入分母，不选择性重跑；Host 级故障停批保全证据。

## 二、启动前的准备（两类共用）

### 1. 凭证隔离 HOME

```bash
bash scripts/setup-pi-home.sh        # 默认建在 ~/.skill-eval/pi-home
```

`~/.skill-eval/pi-home/.pi/agent/auth.json` 须含：
- `minimax-cn` 的 `api_key`（被评模型）
- `xiaomi-token-plan-cn` 的 `api_key`（评委模型）

不触碰真实 `~/.pi` 或 `~/.optracall`。

### 2. Node 解释器

OptraCall Host/worker 需 **Node 25+**。当前解释器不足时用 `--optracall-node /path/to/node25+` 指定。

### 3. OptraCall checkout

提供产品源码 checkout（须已 `npm ci`）。环境准备只读复制它，排除 `node_modules/.git/dist/.runtime/.local`。

### 4. 预检（不产生费用）

```bash
npm run eval -- preflight \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home
```

## 三、skill 测评（完整可用）

测一个 SKILL.md 是否真被激活、激活后是否真改善输出。

### 启动

```bash
npm run eval -- eval \
  --suite suites/optracall-smoke.json \
  --optracall /path/to/OptraCall \
  --optracall-node /path/to/node25+ \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home \
  --repeat 1 --judge-repeat 1
```

- 套件须声明 `optracall` 段（`skillName`、`templateDir`）；目标 skill 取自 checkout 的 `extensions/analysis-assets/<skillName>`。
- 现有套件：`optracall-smoke.json`（单题冒烟）、`optracall-data-analysis-v1.json`（data-analysis 草案）。
- 规模 = `任务数 × repeat × 2` 被评会话 + `任务数 × repeat × judgeRepeat` 评委会话。**真实运行产生费用，开跑前确认规模。**

### 判读

看 `runs/<run-id>/REPORT.md` 与 `summary.json`：
- **激活率**：baseline 0、skill 侧读取 skill 包 = 强激活。
- **断言通过率 / 胜率 / 规则纠偏胜率 / 增益区间**。
- **结论**：`effective` / `inconclusive` / `ineffective`。单题冒烟通常是 `inconclusive`（证链路通，不证有效）。

### Qoder 编排

调用 `/skill:skill-eval-flow`，按状态机 S0→S4 引导（收集输入→环境自检→套件冻结→对照评估→解读报告）。

## 四、memory 测评（完整可用）

测 Agent 能否正确检索、选择、理解、使用跨任务记忆，并抵抗无关/过期/冲突/越权记忆干扰。

### 设计

- **唯一变量**：`read_case_sources`（M6 跨事项经验）能力有无，由 `--disable-experience-learning` Host flag 控制。baseline 关、treatment 开 + 注入合成记忆 Fixture。
- **判据**（行为取证为主）：检索决策、相关性选择、正确使用、来源/可信度识别、过期冲突处理、干扰抵抗。取证器从 native 会话提取 `read_case_sources` find/read 的成功调用（`consulted`＝成功使用记忆；工具不可用时的失败尝试不算）。
- **复用**：OptraCall 后端能力开关模式 + 计分引擎；记忆使用映射为激活率。

### 已实现

- env 能力模式：双 codeRoot 全等，唯一变量由 Host flag 承载。
- execution 能力开关：按 variantId 分侧，baseline 带 `--disable-experience-learning`、treatment 不带。
- runner 按 id 判 baseline（能力模式两侧皆无 skill 也能正确配对）。
- **Fixture 注入器**：向评测 dataRoot 的 Case SQLite 注入合成判断卡片（含 v1→v2 迁移），不碰真实产品数据。
- **记忆行为取证器**：`detectMemoryUsage` 提取 find/read 成功调用与目标。
- memory 套件（`optracall-memory-smoke.json`）+ CLI `memory-eval` 入口。
- 离线端到端验证通过（注入→查读→取证正例成立，基线能力关闭）。
- 契约：[c1-memory-contract](plans/2026-11-15-c1-memory-contract.md)。

### 启动

```bash
npm run eval -- memory-eval \
  --suite suites/optracall-memory-smoke.json \
  --optracall /path/to/OptraCall --optracall-node /path/to/node25+ \
  --model minimax-cn/MiniMax-M3.1-Flash \
  --judge-model xiaomi-token-plan-cn/mimo-v2.6-flash \
  --home ~/.skill-eval/pi-home --repeat 1 --judge-repeat 1
```

- 套件声明 `optracall.capability="memory"` 与 `memoryFixtures`（合成判断卡片）。
- 处理侧自动初始化 Case 存储并注入 Fixture；baseline 不注入、记忆工具关闭。
- 看 `runs/<run-id>/REPORT.md`：激活率＝记忆成功使用率；`cases/memory/<task>/<attempt>/optracall/memory.json` 是行为取证。
- 单题冒烟通常 `inconclusive`（证链路通，不证有效）；正式测评需扩独立任务与重复。

### 离线端到端验证（无费用）

```bash
node --experimental-strip-types scripts/optracall-memory-integration.ts --checkout <checkout> --node <node25+>
```

## 六、产物与重算

`runs/<run-id>/`：
- `cases/<variant>/<task>/<attempt>/`：`events.json`、`output.md`、`result.json`、`deliverable.md`、`optracall/`（native 会话、项目树哈希、usage）。
- `optracall-env/`：双 codeRoot/dataRoot/projectsRoot。
- `optracall-ledger.jsonl`、`budget-ledger.jsonl`、`execution-status.json`、`run-manifest.json`、`summary.json`、`REPORT.md`。

从原始产物重算（不覆盖原报告）：

```bash
npm run eval -- report --run runs/<run-id> --suite-file <套件.json>
```
